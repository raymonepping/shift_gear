# Keep the Dream Alive

*Vault Enterprise on OpenShift — the fifth lab, and the one where the substrate finally disappeared.*

---

> *"No stranger to this place."* — Oasis, *Keep the Dream Alive* (2005)

Article four ended with the words *"This is the last one."* I meant it when I wrote them.

That article closed the Multipass arc: four labs, three virtual machines, eight virtual machines, then the boundary enforced by policy. There was nothing left to prove on Multipass.

But there was something left to prove on the architecture itself. The claim I had been making since article one — that the Vault platform does not know what it runs on — had never been tested against a real substrate change. Every lab was Multipass VMs. The architecture was theoretically substrate-independent. Theoretically.

This is the fifth lab. The same Mac. A different substrate. And a grep command with zero matches that proves the theory was right.

---

## What did not change

The ownership rule is unchanged. Terraform builds the house — anything with an API and a lifecycle: Kubernetes namespaces, Helm releases, Vault structure (mounts, policies, token roles, audit devices). Ansible decorates it — anything with an order and a moment: init, unseal, credentials, people, seeds, proofs. The Vault Secrets Operator delivers secrets to workload pods at runtime. Vault policy enforces the line between what each tool may do.

The seal chain is unchanged. A dedicated seal Vault holds a transit key. The cluster Vault pods reference that key in their Helm values and unseal themselves on restart. The seal agent holds an AppRole credential to rotate its own access — not a cluster Vault token. No seal token ever exists on the cluster. Running `make rotation-proof` twice proves the old secret-id returns 400 and the current one returns 200.

The phase list is unchanged in structure. It interleaves Terraform and Ansible because neither tool alone can build the stack. Terraform cannot init a Vault cluster. Ansible cannot create a Kubernetes namespace. Thirteen phases, in order:

```text
tf      infra
tf      foundation
ansible prepare
tf      workloads
ansible seal-init
tf      seal
ansible agent
ansible bootstrap
tf      platform
ansible identity
ansible configure
ansible ux
ansible validate
```

The gates are unchanged. `make boundary` runs 19 `sys/capabilities-self` checks. Terraform can create mounts and cannot mint a secret-id. Ansible can mint secret-ids and cannot create a mount. The boundary is a Vault policy, not a team agreement.

The Vault Operator pattern is unchanged in its shape. `VaultConnection` declares where Vault lives. `VaultAuth` declares how VSO authenticates (Kubernetes auth, not a token). `VaultStaticSecret` and `VaultDynamicSecret` declare what to sync. The resulting Kubernetes `Secret` objects are mounted into workload pods. The pods have no Vault address in their environment.

What changed was not the patterns. It was the implementation. `systemd` became a Helm release. `firewalld` became a `NetworkPolicy`. A `systemd` timer became a `CronJob`. Ansible stopped SSH-ing to nodes — it connects to the Vault API through a Route or runs commands in-cluster with `kubernetes.core.k8s_exec`.

## The substrate contract

The central idea of this series is that the Vault platform does not know what it runs on. Shift Gear makes that idea operational with a single Terraform root: `terraform/infra/`.

That root reads the running OpenShift cluster and emits a six-field output:

```hcl
output "cluster" {
  value = {
    api_url         = var.api_url
    apps_domain     = local.apps_domain
    pod_cidr        = local.pod_cidr
    kubeconfig_path = var.kubeconfig_path
    ingress_ca_path = local.ingress_ca_path
    registry_host   = "image-registry.openshift-image-registry.svc:5000"
  }
}
```

Three of the six fields are discovered from the running cluster. `apps_domain` comes from `ingresses.config.openshift.io/cluster`. `pod_cidr` comes from `networks.config.openshift.io/cluster`. `ingress_ca_path` is extracted from the `openshift-ingress-operator` secret. Any OpenShift cluster exposes these resources at the same API paths — they are standard, not CRC-specific.

Every Route hostname in the stack is `something.${apps_domain}`. Every CIDR-bound policy and NetworkPolicy uses `${pod_cidr}`. The Terraform provider block uses `${kubeconfig_path}`. No module above `terraform/infra/` has a hardcoded domain, CIDR, or kubeconfig path.

The isolation check:

```sh
grep -rn --include='*.tf' --include='*.yml' --include='*.yaml' \
     --include='*.sh' --include='*.hcl' \
     -E 'crc|vfkit|api\.crc\.testing|apps-crc\.testing' \
     terraform/foundation terraform/workloads terraform/seal \
     terraform/platform ansible policies deploy
```

Expected result: zero matches. `make check` runs this grep. A single match is a build failure.

This is not a new concept. `golden_ticket`'s `lab_nodes` output was the same idea applied to VMs: a map of node names to IP addresses that the rest of the automation consumed without knowing they were Multipass VMs. Shift Gear extends it to a cluster API. The concept is older than this series; the implementation here is its first test against a genuinely different substrate.

**What is proven.** The grep proves that nothing above `terraform/infra/` mentions CRC. It does not prove that `make lab` succeeds on ROSA or vSphere. That proof requires a run on a second cluster. The contract has one implementation today. The isolation is real; the portability is theoretical until the second run happens.

## What OpenShift changed

Not the architecture. The substrate layer.

**No VMs to address directly.** In `golden_ticket`, Ansible SSH-ed to IP addresses from the `lab_nodes` output. In Shift Gear, there are no IP addresses to SSH to. The OpenShift nodes are not accessible from the Mac. Ansible connects to the Vault API through a Route (`https://vault.apps-crc.testing`) and uses `kubernetes.core.k8s_exec` for operations that must run in-cluster — seeding the LDAP directory, for example. The inventory is a set of Vault addresses and OpenShift API URLs, not a list of node IPs. The change required rewriting every Ansible role that previously made a shell connection. None of the role logic changed.

**The Vault Secrets Operator.** In the VM labs, Vault credentials had to reach workloads somehow — through environment variables, through a script, or through a file. None of those options is clean. VSO is the clean option, and it is native to OpenShift: CRDs that declare what to sync, a cluster-scoped operator that does the syncing, Kubernetes Secrets that appear in namespaces without any workload-side code. The workload reads a file. That is all. The workload has no Vault address in its environment. `make verify` checks this for every pod in `sg-workloads` and `sg-app`.

**In-cluster builds.** The Shift Gear console is a containerised Nuxt 3 application. Building it on the Mac and pushing to the in-cluster registry was the straightforward approach; I did not take it. Instead, a `BuildConfig` and an `ImageStream` in `terraform/foundation/` declare the build. `ansible ux` triggers it. The build runs inside the cluster, in the `sg-app` namespace, using the OpenShift builder SA. The evidence files that the console needs — `.build/layers.json`, `.build/validation.json` — cannot be read from the Mac by a pod. Ansible syncs them as a ConfigMap (`sg-evidence`) into `sg-app`. The pod mounts the ConfigMap.

Each of these three changes required real work. The architecture did not require modification.

## The Vault Operator is the third layer

`golden_ticket` has two tools: Terraform and Ansible. Shift Gear has three. Terraform provisions. Ansible configures. The Vault Operator *operates* — continuously, at runtime, without human intervention.

The operation of one `VaultStaticSecret` from CRD definition to workload pod:

```yaml
# In terraform/workloads/main.tf — declared by Terraform
resource "kubernetes_manifest" "vss_app_config" {
  manifest = {
    apiVersion = "secrets.hashicorp.com/v1beta1"
    kind       = "VaultStaticSecret"
    metadata   = { name = "app-config", namespace = "sg-workloads" }
    spec = {
      vaultAuthRef = "sg-vso-auth"
      mount        = "kv"
      path         = "shift-gear/config/app-config"
      destination  = { create = true, name = "app-config" }
    }
  }
}
```

The VSO operator reads this resource. It authenticates to Vault using the Kubernetes projected SA token of the `vso-workloads` service account. It reads `kv/data/shift-gear/config/app-config` in the `shift-gear` namespace. It creates (or updates) the Kubernetes `Secret` named `app-config` in `sg-workloads`. The workload-a pod mounts it read-only.

The rotation moment — from `make wl-a-rotate`:

```sh
vault kv put -mount=kv shift-gear/config/app-config \
  value="$(openssl rand -hex 16)" \
  rotated_at="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

VSO syncs within 30 seconds. The `app-config` Secret is updated. workload-a rolls — because a `spec.template.metadata.annotations` watches the Secret hash, the Deployment detects the change and triggers a rolling update.

No token. No script watching for changes. No Ansible task. The operator keeps the secret current.

## The token boundary on OpenShift

`golden_ticket` article four introduced the boundary: four bootstrap tokens, each scoped by Vault policy to exactly what its tool needs.

Shift Gear keeps the same four tokens. `sg-tf-seal` may create the transit mount and AppRole roles on the seal Vault; it may not mint a secret-id. `sg-ansible-seal` may mint secret-ids and read role-ids; it may not create a mount. `sg-tf-platform` may create Vault mounts and write policies; it may not enable auth methods or write KV data. `sg-ansible-platform` may enable auth methods and write KV data; it may not create a mount or write a policy.

The boundary is wider now. VSO uses Kubernetes auth — the pod's projected SA token is the credential. No Vault token is stored anywhere for VSO. The agent-demo pod uses Vault Agent with Kubernetes auth — same pattern, no stored token. Workload pods hold no credential at all.

`make boundary` produces 19 rows. Sample output (token values redacted):

```text
TOKEN                  VAULT         PATH                                       EXPECT     RESULT
tf-seal                vault-seal    sys/mounts/transit                         allow:create  PASS
tf-seal                vault-seal    auth/approle/role/.../secret-id            deny:update   PASS
ansible-seal           vault-seal    auth/approle/role/.../secret-id            allow:update  PASS
ansible-seal           vault-seal    sys/mounts/transit                         deny:create   PASS
tf-platform            vault         shift-gear/sys/mounts/transit              allow:create  PASS
tf-platform            vault         shift-gear/sys/auth/kubernetes             deny:create   PASS
ansible-platform       vault         shift-gear/sys/auth/kubernetes             allow:create  PASS
ansible-platform       vault         shift-gear/sys/mounts/transit              deny:create   PASS
...
19/19 checks passed
```

The boundary is not a team agreement. It is a policy. Running `make boundary` on a second terminal while another terminal is running `make platform` would show `tf-platform` being denied on the paths Ansible owns. That is the point.

## Drift, both kinds — and a third

Terraform drift: a Helm value changed with `oc edit`, a Vault mount disabled by hand. `make drift` runs `terraform plan -detailed-exitcode` on all five roots. Exit code 2 means drift. The plan shows exactly what changed. `terraform apply` restores it.

Ansible drift: a Keycloak client setting changed in the admin UI, a user added to a second LDAP group. `make drift` runs every Ansible playbook with `--check`. `changed` greater than zero means drift (excluding the allowed exceptions in `idempotency-allow.txt`). The playbook re-applies the change.

A note on Terraform's scope: Terraform does not see objects it never declared. A stray ConfigMap added by an operator, a manually created Service, a pod — invisible to Terraform. Drift detection covers only what the stack owns. This is correct behaviour and a reason to keep the Terraform surface minimal.

OpenShift adds a third kind: **VSO sync drift**. A `Secret` whose content no longer matches the Vault path it came from. This can happen if someone edits the Secret directly or if the Vault path was modified outside the automation. `make verify` catches it by checking each `VaultStaticSecret`'s `status.lastSyncTime` — if it is older than a configurable threshold, the row is flagged `⚠`. A VSO re-sync restores the correct value within the next cycle.

From `docs/operations.md`:

| Tool | Change made | Detected by |
|---|---|---|
| Terraform | `oc edit deployment vault-0` (add label) | `make drift` (tf plan shows diff) |
| Ansible | LDAP group member added via `ldapmodify` | `make drift` (ansible check-mode reports change) |
| VSO | `Secret` content edited manually | `make verify` (`VaultStaticSecret.status.lastSyncTime`) |

## The console learned the substrate

The `golden_ticket` console had a Front door page showing Nginx routes, a Layers page showing phases, and a Cluster page showing VM-level data. The Shift Gear console has the same structure, adapted for OpenShift.

The **Fleet** page shows what Terraform's `workloads` root owns: pod counts and resource totals from the OpenShift API, checked against the `workloads` Terraform output. Every tile traces to a resource declared in `terraform/workloads/`.

The **Layers** page shows the same interleaved Terraform/Ansible phase structure, plus the four gates. Each phase has a duration (from `.build/layers.json`) and an expand arrow showing what it owns and what it produced.

The **Routes** page shows every OpenShift Route with its TLS termination mode and live backend health. Not HAProxy — OpenShift's ingress controller. The termination modes are `passthrough` (Vault), `reencrypt` (Keycloak), and `edge` (the Shift Gear console itself).

The **Operator** page shows the VSO CRD resources: each `VaultStaticSecret` and `VaultDynamicSecret` with its `lastSyncTime`, sync status, and a link to the destination Secret. This is the page to watch during `make wl-a-rotate`.

## Surprises

**The clock drift cascade.** After a Mac sleep, the CRC VM clock can jump forward by more than the 5-minute leeway on Kubernetes projected SA tokens. Vault returns 403 on Kubernetes auth. The fix is in `scripts/crc-post-start.sh`: chrony is configured with `makestep 1.0 -1` and `maxpoll 6`, which allows immediate step-correction on every CRC restart. Running `make crc-up` applies this automatically.

**The `serverAuth + clientAuth` EKU requirement.** The seal agent's mTLS listener requires client certificates. Vault pods present their own TLS certificate as a client certificate when connecting to the seal agent. A certificate with only `serverAuth` in its extended key usage fails the mTLS handshake. All Vault pod certs are generated with both EKUs. This is not in the documentation for the transit seal; it comes from the TLS handshake error message.

**The VSO CSV gate.** Applying a `VaultConnection` resource while the Vault Secrets Operator CSV is in `Installing` phase produces `no kind "VaultConnection" is registered for version "[secrets.hashicorp.com/v1beta1"`. The error message does not mention the CSV. The fix — poll until the CSV reaches `Succeeded` before proceeding — is now in `ansible prepare` with a 20-attempt 30-second retry loop.

**Keycloak `givenName`, not `cn`.** The default Keycloak LDAP mapper for `firstName` uses the `cn` attribute. For users in this lab, `cn` is the full name (`ada lovelace`). The OIDC `given_name` claim was `ada lovelace`; Vault's `bound_claims` check on `given_name = ada` failed. Mapping `firstName` from the `givenName` attribute fixes it. This came from `red_doors`.

## What the series taught, all five together

`multi_pass`: *contracts win.* A stable output contract — a map of names to endpoints — lets tools compose without coupling. The consumer does not know what the producer is.

`red_pass`: *evidence wins.* Nothing is green until something checked it. A badge without a drawer is a lie. Every gate writes a JSON file; a failed run still produces an inspectable result.

The comparison (`03.md`): *a platform needs both answers.* Lifecycle questions belong to Terraform. Order-and-moment questions belong to Ansible. Mixing them produces plans that fail because the infrastructure they need does not yet exist.

`golden_ticket`: *the boundary is a policy, not a convention.* A cultural rule can be overridden by a deadline. A Vault policy cannot. `make boundary` runs 19 capability checks on every build.

`shift_gear`: *the substrate is not the architecture.* The Vault platform, the Ansible playbooks, and the VSO resources know only the six-field contract. On another OpenShift cluster, only `terraform/infra/` would change. One implementation so far — the isolation is proven, the portability is the next test.

At enterprise scale, this translates directly. HCP Terraform workspaces replace local state files and add run triggers that enforce phase order. Ansible Automation Platform replaces `ansible-run.sh` and adds RBAC, credential injection, and job history. The Vault Operator scales to every namespace in the cluster — the same CRDs, the same policies, hundreds of workloads without a credential in any pod. The substrate contract means a migration from CRC to ROSA requires one Terraform variable change and one `make infra` run. `docs/enterprise.md` in this repository maps every lab mechanism to its enterprise counterpart in the same table structure used in `golden_ticket`.
